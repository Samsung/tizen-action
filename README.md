# Tizen Action Compiler

A self-contained, multi-platform compiler repository designed to store the Tizen Action Framework compiler and driver binaries (`actionc`, `action2tidl`, and `tidlc`) and automate their installation onto Linux, macOS, and Windows 64-bit host systems.

## Binaries Included

* **`actionc`**: The orchestrator driver to compile and output complete C/C++/C#/Dart/JavaScript stubs (Linux, macOS & Windows 64-bit).
* **`action2tidl`**: Converts Tizen `.action` models into `.tidl` interfaces (Linux, macOS & Windows 64-bit).
* **`tidlc`**: The primary TIDL compiler generating stubs, proxies, and IPC bindings (Linux, macOS & Windows 64-bit).

The binaries live under `bin/linux/`, `bin/macos/`, and `bin/windows/`. The macOS binaries are x86_64 Mach-O executables built for macOS 26 or later and run on Apple silicon through Rosetta 2.

The action/entity schemas are not part of this repository: the installers fetch the set matching the attached device's `tizen-action` version from the data repository named in `data-repo.conf` (see [Schema data repository](#schema-data-repository)), so the installed binaries are reused across device updates.

## Environment Specifications

The `actionc` orchestrator utilizes and resolves several official environment variables to operate in a self-contained and robust manner:

| Setting | Option | Environment | Default / Value |
| --- | --- | --- | --- |
| Action/entity schemas | `-d, --data-dir` | `ACTIONC_DATA_DIR` | `$HOME/.action-tools/data` (Windows: `$HOME\.action-tools\data`) |
| action2tidl binary | — | `ACTIONC_ACTION2TIDL` | `$HOME/.action-tools/action2tidl` (Windows: `$HOME\.action-tools\action2tidl.exe`) |
| tidlc binary | — | `ACTIONC_TIDLC` | `$HOME/.action-tools/tidlc` (Windows: `$HOME\.action-tools\tidlc.exe`) |

## Schema data repository

Stubs must be generated from the same action/entity schemas the device runs, and the device's `tizen-action` moves independently of this compiler. Rather than shipping a schema snapshot with every compiler release, the installers fetch the data as their last step through the bundled `actionc-sync` helper, which:

1. reads the `tizen-action` version off the attached device (`sdb shell rpm -q tizen-action`; `SDB_SERIAL` picks one of several devices),
2. fetches the data repository with `git` (a shallow clone kept under `~/.action-tools/data-repo`),
3. picks the matching version directory and installs it into `~/.action-tools/data`, where `actionc` reads it.

So a plain `./install.sh` (or `./install-macos.sh`, `install.bat`) leaves the data matching the attached device. Without a device, network, or a matching version the installers warn and finish anyway; `actionc` then has no schemas until an install with a device attached succeeds (schemas from an earlier install, if any, are left in place). Re-run the installer after switching devices or after a device update; the fetch is a no-op when the installed data already matches. `git` must be on `PATH` on every platform.

The data repository holds one directory per `tizen-action` version, each with the layout `actionc` expects in its data directory:

```
<version>/actions/*.action
<version>/entities/*.entity
<version>/action.seq
```

The directory named exactly like the device version is used when it exists; otherwise the highest version with the same `<major>.<minor>` that is not newer than the device, since `REQUIREMENTS` pins compatibility to a minor line. A device with no matching line is an error listing what is available.

Which repository and which version are used comes from `data-repo.conf`, installed next to the binaries:

```
DATA_REPO=https://github.com/Samsung/tizen-action.git
DATA_REPO_BRANCH=data
DATA_VERSION=
```

The schemas live on the `data` branch of the same repository that holds this toolchain on `main`. Keeping them on their own branch lets `actionc-sync` shallow-clone the schemas alone, without the compiler binaries, and lets the two move on their own release cadences. `DATA_VERSION` left empty (or `auto`) means "whatever the attached device runs"; set it to pin a `tizen-action` version, for example on a build machine without a device. The version actually used is resolved in this order: `ACTIONC_DATA_VERSION`, `DATA_VERSION` in the file, then the device. `ACTIONC_DATA_REPO`, `ACTIONC_DATA_REPO_BRANCH` and `ACTIONC_DATA_VERSION` in the environment override the file for one user or one shell. The installed data records where it came from in `data/DATA_VERSION` and `data/DATA_SOURCE`, which `version.sh` reports.

## Version

Two files at the repository root are the single source of truth for a release; nothing else restates them:

| File | Holds |
| --- | --- |
| `VERSION` | The compiler release version |
| `REQUIREMENTS` | The on-device (target) component versions this release expects, one `<component> <operator> <version>` per line |

Stubs generated by the compiler target a specific Action Framework interface, so a target running an older `tizen-action` than `REQUIREMENTS` declares will reject them. **Cutting a release means editing these two files** — `install.sh` / `install-macos.sh` / `install.bat` copy both to `~/.action-tools`, and `version.sh` reads them.

When a device is attached over `sdb`, `version.sh` also reads each component's installed version off the target and flags whether the compiler is compatible:

```
Target requirements:
  ✗ tizen-action >= 1.9.2 (device: 1.8.0)
  Connected device does not meet this compiler's requirements.
```

The check is skipped (requirements are just listed) when `sdb` is missing, no device is attached, or the device does not answer. With several devices attached, set `SDB_SERIAL` to choose one:

```bash
SDB_SERIAL=10000000c6427abc ./version.sh
```

### Checking Version

Use the provided version check script to see complete version information:

```bash
./version.sh
```

This displays:
- Repository compiler version
- Installed compiler version
- Target requirements declared by this release, checked against the attached device
- Schema data in use (synced `tizen-action` version)
- Individual binary versions (actionc, action2tidl, tidlc)
- Environment variable settings

Alternatively, check individual versions:

```bash
actionc -v                      # binary version
cat ~/.action-tools/VERSION     # installed compiler version (after installation)
```

## Installation

### Linux

You can install these tools inside a dedicated, isolated directory (`~/.action-tools`) and persistently configure your shell profile (`~/.bashrc` and `~/.profile`) by running the provided installation script:

```bash
./install.sh
```

Once complete, refresh your current terminal session immediately:

```bash
source ~/.bashrc
```

### macOS

macOS terminals open login shells, and zsh has been the default shell since Catalina, so the macOS script installs into the same `~/.action-tools` directory but configures `~/.zprofile` (zsh) and `~/.bash_profile` (bash) instead of `~/.bashrc`:

```bash
./install-macos.sh
```

Once complete, refresh your current terminal session immediately:

```bash
source ~/.zprofile
```

On Apple silicon the x86_64 binaries need Rosetta 2; the script warns when it is missing and it can be installed with `softwareupdate --install-rosetta --agree-to-license`. To remove the compiler and the profile entries, run `./uninstall-macos.sh`.

### Windows (64-bit)

Double-click or run the provided Windows Command Batch installation script. This script copies the Windows binaries to `%USERPROFILE%\.action-tools` and persistently configures your User Environment variables:

```cmd
install.bat
```

Once complete, restart your terminal or shell session to apply the changes.

## Claude Code Skill

The repository ships a Claude Code skill at `.claude/skills/create-action-app/` that
scaffolds an Action Framework provider app with this compiler. Run Claude Code from
this directory (or a parent) and ask for an action provider app — or invoke it directly:

```
/create-action-app
```

It covers C#, C++, JavaScript, and Dart providers: stub generation with `actionc`,
the service implementation, per-action `action/provider` manifest registration, and
`gen.sh`/`run.sh` build-deploy-test scripts. Language templates and the `.action` /
`.entity` schema notes live under `.claude/skills/create-action-app/references/`.
